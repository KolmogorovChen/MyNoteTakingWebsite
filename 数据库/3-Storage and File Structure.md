# 3-Storage and File Structure

核心问题：**大量表数据实际存在哪里，DBMS 怎样读取和修改它们**？

① 存储层次与 I/O → ② 记录布局 → ③ 页与槽目录 → ④ 文件组织 → ⑤ 缓冲池 → ⑥ 页数与 I/O 估算。

逻辑表 → 记录 → 页 → 文件；执行查询时，缓冲池管理页在内存与持久化存储之间的流动。

## 一、存储层次与磁盘 I/O

我们沿着一个具体过程展开：**执行一条查询时，数据库怎样把存储设备中的数据取出来，交给 CPU 处理**？

```sql
SELECT name FROM Student WHERE sid = 'S1'; 
```

从 SQL 的角度看，这是查找一名学生的姓名。

从存储的角度看，需要解决三个问题：**数据保存在哪里、每次读取多少、怎样读取更省时间。**

--------

### 1. 存储层次：内存与持久化存储

**（1）数据长期保存在哪里**

`Student` 是我们在关系模型中看到的表。在实际存储中，它需要按照一定的格式保存在数据库文件中。

这些文件通常放在 HDD 或 SSD 等**持久化存储设备**上。“持久化”意味着：关闭数据库或断电后，已经可靠保存的数据仍然存在。

但数据库执行查询时，不能只让数据停留在存储设备中。数据库程序需要把相关数据读入内存，供 CPU 处理。

基本过程是：
$$
\text{存储设备保存数据} \rightarrow \text{数据读入内存} \rightarrow \text{CPU 检查条件、计算并生成结果}
$$

| 存储位置               | 主要特点                                       | 在数据库中的作用             |
| ---------------------- | ---------------------------------------------- | ---------------------------- |
| 内存（RAM）            | 访问快，断电后内容通常丢失                     | 存放正在处理、近期访问的数据 |
| 持久化存储（HDD、SSD） | 容量通常更大，单位容量成本更低，断电后保留数据 | 长期保存数据库文件           |

**（2）为什么需要同时使用内存和持久化存储**

数据库可能有几百 GB，甚至更多数据，而可供使用的内存有限。

数据库执行查询时，不能只让数据停留在存储设备中。数据库程序需要把相关数据读入内存，供 CPU 处理。

因此，常见做法是：**完整数据保存在持久化存储中，当前需要的部分放入内存**。

| 对比         | 内存（RAM）        | 持久化存储（HDD、SSD） |
| ------------ | ------------------ | ---------------------- |
| 访问速度     | 快                 | 通常比内存慢           |
| 单位容量成本 | 较高               | 较低                   |
| 容量         | 通常较小           | 通常较大               |
| 断电后       | 内容通常丢失       | 保留已可靠写入的数据   |
| 主要作用     | 支持当前的数据处理 | 长期保存数据库文件     |

内存中的数据会随工作需要变化，不必一次装下整个数据库。

**（3）访问数据会产生 I/O 成本**

这里的 I/O，主要指数据库对存储设备的读取和写入：

- **读 I/O**：从存储设备读取数据，送入内存。
- **写 I/O**：将需要保存的数据写入存储设备。

例如：

```sql
SELECT name FROM Student WHERE sid = 'S1';
```

数据库找到 S1 所在的数据页后，需要判断该页是否已经在内存中：

- **已经在内存中**：可以直接读取并处理。
- **尚未在内存中**：需要发起读取，并等待设备返回数据，再处理。

这种对存储设备进行读取或写入的操作，就是这里所说的 **I/O**。

I/O 成本来自设备访问、请求处理和数据传输等过程。访问持久化存储通常比访问内存慢，因此，等待 I/O 可能占据查询时间的很大一部分。

因此，查询耗时既包括 CPU 处理数据的时间，也可能包括等待 I/O 的时间。**数据处理本身很简单时，等待读取反而可能成为主要开销。**

--------------

### 2. 数据库页与 I/O 的基本单位

知道数据需要从存储设备读入内存后，下一个问题是：**每次读入多少**？

**（1）数据库页**

数据库通常把文件划分为固定大小的页（page），**以页为单位组织、读取和缓存数据**。

例如，假设一个数据库使用 8 KB 的页，那么一个页中可以保存多条学生记录，以及管理这些记录所需的信息。可以理解为：

```markdown
Student 表的数据文件
    ├─ 第 1 页：若干条学生记录
    ├─ 第 2 页：若干条学生记录
    └─ 第 3 页：若干条学生记录
```

那么读取一个数据页，就是把这一页的内容读入内存。具体页大小取决于数据库系统和配置。

**（2）数据读写和缓冲管理的基本单位**

为什么查询一条记录，往往需要读取整个页？因为在常用的数据库存储模型中，**页是数据读写和缓冲管理的基本单位**。

继续看查询 S1 姓名的例子。这里先假设数据库已经确定：S1 位于第 20 页。如何确定位置，会在后续的文件组织和索引中讨论。

接下来的过程是：

1. 检查第 20 页是否已经在内存中。
2. 如果没有，将第 20 页读入内存。
3. 在这一页中取得 S1 的记录，取出 `name`。
4. 返回查询结果。

虽然查询只需要一个姓名，但通常需要读取包含它的整个页。

这里的“基本单位”指**数据库层面的页**；底层设备有自己的读写单位，一次 I/O 请求也可能批量传输多个页。

**（3）读入内存的页，会保存在哪里**

数据库通常用一块内存区域保存数据页，称为**缓冲池（buffer pool）**。

如果第 20 页已经在缓冲池中，再次访问它时就可以直接使用，这称为**缓存命中**。如果没有，就需要从存储设备读取。

因此，同一条查询执行两次，第二次可能更快：它需要的页可能已经留在内存中。

缓冲池容量有限。空间不足时，数据库会选择一些页移出，为新读入的页腾出空间。

**（4）记录、数据库页和设备块的区别**

**数据库要读的是“一整个数据库页”，操作系统和磁盘会把它拆成若干个设备块/扇区来完成传输**

| 概念                           | 属于哪一层       | 它是什么                                     |
| ------------------------------ | ---------------- | -------------------------------------------- |
| 记录 / 行                      | 数据库逻辑层     | 表中的一行数据，比如一个学生、一笔订单       |
| 数据库页 / 块                  | 数据库引擎层     | 数据库管理数据、缓存数据、读写磁盘的最小单位 |
| 设备块 (block) / 扇区 (sector) | 操作系统和磁盘层 | 文件系统或磁盘硬件读写磁盘的最小单位         |

假设你要查学生 `S1` 的姓名：

1. 数据库先确定 `S1` 这条记录存在哪个 **数据库页** 里；
2. 如果这个页不在内存缓冲池中，数据库会发出 I/O 请求；
3. 操作系统和磁盘会按 **设备块/扇区** 把数据从磁盘读上来；
4. 整个数据库页进入内存后，数据库再从页里取出 `S1` 的姓名。

以 MySQL InnoDB 默认 16KB 页、文件系统块 4KB、磁盘扇区 512B 为例：

| 层级              | 单位          | 这一次查询中发生了什么             |
| :---------------- | :------------ | :--------------------------------- |
| 数据库            | 数据库页 16KB | 需要把包含 S1 的那一整页读入缓冲池 |
| 操作系统/文件系统 | 4KB 块        | 16KB 页通常被拆成 4 个 4KB 块传输  |
| 磁盘              | 512B 扇区     | 这 16KB 对应 32 个 512B 扇区       |

**（5）一次完整的数据读取**

一次完整的读取数据，可以按“逻辑读 → 物理读 → 数据返回”来理解。
$$
\text{客户端 SQL}
\;\xrightarrow{\text{查询请求}}\;
\text{数据库引擎}
\;\xrightarrow{\text{定位目标页}}\;
\text{检查缓冲池}
\;\begin{cases}
\text{命中} \Rightarrow \text{直接从内存读取页}\\
\text{未命中} \Rightarrow 
\text{操作系统/文件系统}
\;\underset{\text{返回数据页}}{\overset{\text{I/O 请求}}{\rightleftharpoons}}\;
\text{磁盘}
\end{cases}
$$
**第一步：客户端发出查询**

比如执行：

```sql
SELECT name FROM students WHERE sid = 1;
```

客户端把 SQL 发给数据库服务器。数据库首先要知道：**这条记录在哪个表、哪个索引、哪个页里**。

**第二步：数据库解析并选择访问路径**

数据库会先解析 SQL，然后决定怎么取数据：

- 如果有索引，可能走 **索引查找**；
- 如果没有索引，可能走 **全表扫描**；
- 最终都会落到某个 **数据库页** 上。

**第三步：检查缓冲池：逻辑读**

数据库不会立刻读磁盘，而是先检查 **缓冲池 Buffer Pool**：

$$
\text{需要访问的数据库页}
\;\xrightarrow{\text{是否在缓冲池？}}\;
\begin{cases}
\text{在} \Rightarrow \text{逻辑读，直接从内存返回}\\
\text{不在} \Rightarrow \text{物理读，需要从磁盘读取}
\end{cases}
$$

如果这个页已经在缓冲池里，就直接从内存中取数据，这叫 **逻辑读**。

**第四步：缓冲池未命中：发起物理读**

如果页不在缓冲池里，数据库就会向操作系统发起读请求：

$$
\text{数据库引擎}
\;\underset{\text{返回数据}}{\overset{\text{读请求}}{\rightleftharpoons}}\;
\text{操作系统}
\;\underset{\text{返回数据}}{\overset{\text{I/O 请求}}{\rightleftharpoons}}\;
\text{磁盘}
$$

磁盘上的数据会按 **扇区/设备块** 被读上来，经过文件系统进入内存，最终把 **整个数据库页** 放入缓冲池。

**第五步：从页中取出记录**

页进入缓冲池后，数据库再从这个页里寻找目标记录。比如页里有多条学生记录，数据库通过行偏移定位到 `sid = 1` 的记录，取出相应的 `name` 属性。

**第六步：返回查询结果**

最后，数据库把结果返回给客户端：

$$
\text{磁盘数据页}
\;\rightarrow\;
\text{操作系统}
\;\rightarrow\;
\text{数据库缓冲池}
\;\rightarrow\;
\text{页内记录}
\;\rightarrow\;
\text{客户端结果集}
$$

### 3.  顺序访问、随机访问与 I/O 成本

即使读取的页数相同，读取顺序不同，耗时也可能不同。

**（1）顺序访问：连续读取相邻位置的数据页**
$$
\text{第 20 页} \rightarrow \text{第 21 页} \rightarrow \text{第 22 页} \rightarrow \text{第 23 页}
$$
如果这些数据页在存储位置上相邻，数据库就可以连续、批量地读取它们，还可以提前读取接下来可能用到的数据页，这称为**预读**。

扫描整张表时，通常可以利用这种访问方式。

**（2）随机访问：跳转到分散的位置读取数据页**
$$
\text{第 20 页} \rightarrow \text{第 51 页} \rightarrow \text{第 800 页} \rightarrow \text{第 123 页}
$$
随机访问为什么可能更慢？以机械硬盘 HDD（Hard Disk Drive） 为例，读取数据大致涉及三个步骤：

1. **寻道**：磁头移动到目标磁道。
2. **旋转等待**：等待目标数据转到磁头下方。
3. **传输**：把数据读取出来。

因此，可以粗略理解为：
$$
\text{一次读取的时间 ≈ 定位等待时间 + 数据传输时间}
$$
连续读取一段数据时，可以把定位开销分摊到许多页上；读取分散位置的数据时，则可能反复定位。

这解释了为什么在 HDD 上，读取同样多的页，顺序访问通常比随机访问快。

SSD（Solid State Drive） 没有磁头移动和旋转等待，随机访问的劣势通常小得多。不过，连续、批量读取仍常有优势，具体差距取决于设备和请求方式。

------

**（3）比较总成本，还要看读取量**

顺序访问通常更高效，但不能只凭“顺序”或“随机”判断整个查询谁更快。

假设 `Student` 表有 1,000 个数据页，而且相关页都未缓存：

| 查询情况                   | 可能的读取方式                           | 成本特点                 |
| -------------------------- | ---------------------------------------- | ------------------------ |
| 查一名学生，能通过索引定位 | 读取少量索引页和数据页，可能涉及随机访问 | 读取量很小               |
| 读取全体学生               | 顺序扫描约 1,000 个数据页                | 读取量大，但适合连续传输 |
| 查大量分散的学生           | 反复访问许多分散的数据页                 | 可能累积大量随机访问开销 |

这里的**索引**，可以先理解为帮助数据库定位记录的辅助结构。

如果只需要少量数据，定位后读取少数页通常更划算。如果所需记录遍布大部分数据页，反复跳转读取，就可能比顺序扫描整张表更慢。

数据库选择访问方式时，需要结合**要读取的页数、页的分布、缓存情况和设备特性**估算总成本。
